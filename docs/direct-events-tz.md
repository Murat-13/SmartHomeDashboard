# ТЗ: прямые события с камер (вебхук) — звонок без Home Assistant

Решения приняты владельцем в чате 19.11.2026 («через вебхук», «профессионально и универсально», решения по
умолчанию — ниже). Проверка возможностей камеры — запись журнала AGENTS.md от 19.11.2026 «Reolink — звонок напрямую
с камеры». При расхождении — уточнить у владельца.

Статус: **ТЗ, к работе не приступали.**

## Цель

Звонок домофона (и позже другие события камеры) приходит на планшет **напрямую с камеры по домашней сети** —
без Home Assistant и без интернета, быстрее, чем через HA. HA остаётся вторым источником: если прямой путь не работает,
всё работает как сейчас.

Решения владельца (по умолчанию):
- основной путь — **вебхук**: камера сама шлёт событие на планшет;
- камеру настраивает **само приложение** (логин и пароль камеры у планшета уже есть — видео);
- **HA — второй источник**, не отключается; срабатывает первый, повтор отбрасывается;
- запасной **опрос камеры** — только когда вебхук нездоров;
- порт приёмника **8765**, меняется в настройках;
- универсально: отдельные «драйверы» производителей; первый — Reolink;
- по этапам, сначала только этап 1.

Вне рамок: облачные push производителей, фирменный протокол Reolink (порт 9000), двусторонняя связь, доступ к
приёмнику из интернета.

## Что проверено на камере владельца (19.11.2026)

Reolink Video Doorbell PoE, прошивка v3.0.0.6460. HTTP API — `https://<камера>/cgi-bin/api.cgi?cmd=…&token=…`
(`/api.cgi` принимает вход, но остальные команды — «please login first»). HTTP (80) выключен, HTTPS (443) включён.

- `Login` → токен; `GetDevInfo` — модель, тип `BELL`, прошивка.
- `GetWebHook {"channel":0}` → `{"WebHook":[{"index":0..3,"hookUrl":"","hookBody":"","bCustom":0,"indexEnable":-1}],
  "channel":0}` — 4 слота, пустой слот: `hookUrl ""`, `indexEnable -1`.
- `SetWebHook {"WebHook":{"channel":0,"index":N,"hookUrl":"http://…","bCustom":0,"hookBody":"","indexEnable":1}}` —
  принят, проверен чтением; тем же вызовом с исходными значениями слот возвращён.
- Вебхук: `POST`, `Content-Type: application/json`, тело
  `{"alarm":{"alarmTime":"2026-11-19T15:12:35.000+0000","channel":0,"channelName":…,"device":…,"deviceModel":…,
  "message":…,"name":"Visitor Alert","title":"Visitor message","type":"VISITOR"}}`. Типы: `VISITOR` (кнопка),
  `PEOPLE`; ожидаются и другие (`VEHICLE`, `DOG_CAT`, `MD`) — проверить на этапе 2.
- Каждое нажатие — отдельный вебхук, на 0,2–0,4 с раньше опроса каждые 0,2 с.
- `GetEvents {"channel":0}` → `visitor.alarm_state` 1 ≈ 15 с после нажатия; `md`, `ai.people/vehicle/dog_cat`.
- `TestWebHook` → «test failed» (-100) — для проверки настройки не годится.
- ONVIF выключен (`GetOnvif` — не поддерживается); `GetAbility` содержит `supportWebhook`.

## Архитектура

### События камеры

Общий поток событий вместо прямого чтения сущностей HA потребителями:

```
источники ──► CameraEvents (слияние, дедупликация) ──► звонок (DoorbellHub/DoorbellMonitor), запись (RecordingEvents)
   ├─ HA: сущности плитки (как сейчас: visitor, person, vehicle, animal, motion — переход выкл→вкл)
   ├─ вебхук камеры (CameraHookServer + драйвер)
   └─ опрос камеры (драйвер; только когда вебхук нездоров)
```

- Событие: камера (id плитки), тип (`RING`, `PERSON`, `VEHICLE`, `ANIMAL`, `MOTION`), источник, время прихода.
- **Звонок:** срабатывает первый источник. Повтор того же нажатия из другого источника отбрасывается, если пришёл
  в пределах окна слияния (у Reolink HA и опрос держат «вкл» ~15 с — окно до конца этого «вкл» у источника, но не
  дольше 20 с). Новое нажатие (новый вебхук) после прежнего дребезга 3 с звонит снова — как повторный звонок сейчас.
- Остальное поведение звонка (мелодия, голос, окно, тихие часы, пропущенные, автосвет) — без изменений.
- Источник каждого звонка пишется в журнал приложения (без адресов и секретов) — для проверки, что пришло первым.

### Приёмник на планшете (`CameraHookServer`)

- Один на приложение; открыт, пока хотя бы у одной плитки включены прямые события. Порт 8765 (настройка «Устройство»).
- Живёт столько же, сколько панель 24/7 (вместе с панелью или службой записи — выбрать при реализации, чтобы не
  останавливался при затемнении и на экранах настроек). Без новых разрешений (INTERNET уже есть).
- Путь `/cam/<секрет>`; секрет — 128 бит случайно, свой у каждой пары «планшет + камера».
- Принимает только: `POST`, тело ≤ 16 КБ, адрес отправителя = адрес камеры этой плитки (имя из адреса RTSP
  разрешается заранее и при смене сети), известный секрет. Остальное — 404 без подробностей; не чаще N запросов/с.
- Ответ камере — сразу `200`, разбор и события — после ответа.
- Ошибка открытия порта (занят) — статус в редакторе и «Устройстве», звонок идёт через HA.

### Драйверы производителей

Интерфейс (по одному классу на производителя): определить камеру; прописать вебхук; проверить, что он на месте;
убрать свой вебхук; разобрать запрос камеры в события; опросить состояние (запасной путь).

**Reolink (этап 1):**
- определение: `Login` + `GetDevInfo`;
- установка: `GetWebHook`; свой слот — тот, где `hookUrl` содержит наш секрет; иначе первый пустой
  (`hookUrl ""`); занятые чужие слоты не трогаем; нет свободного — понятная ошибка «Все 4 слота вебхука заняты»;
  `SetWebHook` и обязательная проверка чтением;
- проверка: наш слот на месте, адрес планшета и порт актуальны, `indexEnable 1`;
- удаление: только свой слот, исходные значения пустого слота;
- разбор: `alarm.type` → `VISITOR`→RING, `PEOPLE`→PERSON, `VEHICLE`→VEHICLE, `DOG_CAT`→ANIMAL, `MD`→MOTION;
  неизвестное — в журнал и пропуск;
- опрос (запасной): `GetEvents` раз в 1 с, событие — переход 0→1;
- токен API живёт ограниченно — повторный вход при отказе; HTTPS с самоподписанным сертификатом — доверять
  только адресу этой камеры;
- не держать сессию API постоянно, кроме запасного опроса.

Позже: Hikvision (ISAPI, отправка тревог на HTTP-адрес), «свой вебхук» (панель показывает адрес и пример запроса
для автоматизаций HA, ESP32 и т. п.).

## Настройка в приложении

Редактор плитки «Домофон», раздел **«Прямые события с камеры»** (виден, если задан адрес RTSP и логин):
- переключатель «Получать звонок напрямую с камеры» (по умолчанию выкл.);
- при включении: определение камеры («Reolink Video Doorbell PoE, прошивка …»), установка вебхука, проверка;
  прогресс и итог понятными словами; ошибка — что делать (неверный пароль, камера не отвечает, нет свободного слота,
  порт занят);
- статус: «Подключено · последнее событие 18:12 (звонок)» / «Ожидание событий» / жёлтый «Нужно внимание: …» /
  «Выключено»;
- кнопка «Проверить» — самопроверка сейчас; выключение — удаление своего вебхука из камеры.

Изменения применяются кнопкой «Сохранить», как остальное в редакторе. Удаление плитки — удаление своего вебхука.

**Хранение.** Флаг «прямые события на этом планшете», секрет и номер слота — локально на планшете, вне резервных
копий и экспорта (как «Записывать на этом планшете»): у каждого планшета свой секрет и свой слот. Формат конфигурации
плиток — только новые необязательные ключи (если понадобятся), старые плитки читаются как раньше. Хранилище секретов
(`SecretStore`) не меняется.

## Надёжность и самопроверка

- Самопроверка вебхука: при запуске панели, раз в 15 мин, при смене сети и адреса планшета, по кнопке «Проверить».
  Адрес планшета сменился — вебхук в камере обновляется сам; в подсказке — закрепить адрес планшета в роутере.
- Вебхук нездоров (нет на месте, камера не отвечает на проверку, приёмник не открылся) — статус жёлтый, включается
  запасной опрос; звонок дополнительно идёт через HA. Восстановился — опрос выключается.
- Камера сброшена или чужой слот перезаписал наш — самопроверка восстанавливает (если есть свободный слот).
- Никаких секретов, токенов и адресов в журнале приложения, в отчётах и в репозитории.

## Этапы и приёмка

**Этап 1 — звонок.** `CameraEvents` (слияние HA + вебхук + запасной опрос), `CameraHookServer`, драйвер Reolink,
раздел в редакторе со статусом, самопроверка, журнал источника звонка.
Приёмка:
- автотесты: поддельная камера Reolink (API и отправка вебхука) в JVM-тестах — установка в свободный слот, свой слот
  находится повторно, чужие не трогаются, нет свободного, удаление, смена адреса планшета, повторный вход;
  приёмник — чужой адрес, неверный секрет, большое тело, мусорный JSON; слияние — вебхук + HA одно нажатие = один
  звонок, два нажатия = два звонка, HA без вебхука = звонок как раньше; полный прогон проекта;
- на планшете с Reolink владельца (с разрешения, после экспорта настроек): включение в редакторе, звонок по кнопке
  с выключенным HA (или без связи с ним) — звонит; с HA — один звонок; задержка по журналу; выключение — слот камеры
  пуст; перезапуск панели и смена Wi-Fi — вебхук восстановлен.

**Этап 2 — события в запись.** Человек, машина, животное, движение из вебхука — в запуск HD-записи
(`RecordingEvents`) через тот же `CameraEvents`.

**Этап 3 — другие производители.** Драйвер Hikvision, «свой вебхук».

## Риски

- Новая прошивка Reolink может изменить формат API или вебхука — драйвер разбирает мягко, неизвестное игнорирует;
  HA остаётся вторым источником.
- Вебхук идёт открытым HTTP внутри домашней сети; защита — секретный путь и проверка адреса камеры.
- Адрес планшета по DHCP может смениться — самопроверка и подсказка закрепить адрес.
- Приёмник должен работать 24/7 вместе с панелью — проверить затемнение, экраны настроек, перезапуск процесса.
